# Where Cherry Pick hooks into Stash

Checked against the Stash source for v0.31.1 and the develop branch of 2026-10-15. Paths are relative to `ui/v2.5/src` unless they start with `pkg/`, `internal/` or `graphql/`.

## How patches run

- React calls a component as `(props, secondArg)`. Every patch on it gets the arguments as the before patches left them, so their number is not fixed (`patch.tsx:86-105`).
- `patch.before(name, fn)`: `fn(...args)` must return an array, the new argument list, which replaces the arguments for every later patch. Return `[newProps, ...rest]` to keep the second argument; Stash Curator returned `[newProps]` alone until 0.40.2.
- `patch.instead(name, fn)`: called as `fn(...args, next)`. `next` is the original function, or the next plugin's `instead`; call it as a function, never render it as `<Next />`, which remounts the subtree on every render once two plugins patch the same component.
- `patch.after(name, fn)`: called as `fn(...args, result)`; it returns what renders. The result comes after the arguments, which is third only when no before patch dropped one: beside Curator before 0.40.2 it was the second. Stash appends it with `args.concat(result)`, which spreads an array, so when an earlier after patch returns one, each item arrives as an argument of its own. Xenith 3.2.0's patch on `MainNavBar.UtilityItems` returns `[result, host]`, the host of its dialog: a patch after it that reads only the third argument drops the host and Xenith's dialog opens empty, and one that reads only the last drops Stash's own Settings, Stats and Donate buttons. Cherry Pick registers every after patch through `patchAfter` (`runtime/api.js`), which passes `(props, result)` with the result rebuilt from every argument after props that renders something (React's second argument is `{}` or a ref, never one), in a fragment when there are several.
- All before patches run before any after patch, whatever order the plugins load in.
- Patches run inside the patched component's render, so hooks called in a patch body become that component's hooks. Cherry Pick's patches only return elements of its own components, which hold their own hooks and state.
- Patching a name that does not exist does nothing, and patches registered before a lazy-loaded module loads still apply.
- `PluginApi.Event` dispatches one event, `stash:location`, on every route change. The first one fires before plugin scripts load, so the plugin reads `window.location` at start.

## Watch This's player

Checked against `components/ScenePlayer/` in v0.31.1.

- `PluginApi.loadableComponents.ScenePlayer` imports `components/ScenePlayer/ScenePlayer` (`pluginApi.tsx:110`), whose `PatchComponent("ScenePlayer", …)` registers it in `PluginApi.components` when the module loads (`patch.tsx`), so `hooks.useLoadComponents([ScenePlayer])` and then `components.ScenePlayer` give Stash's own player, with every plugin's patches on it. Its props are `scene` (`SceneDataFragment`, what `GQL.useFindSceneQuery` returns for the scene page), `hideScrubberOverride`, `autoplay`, `permitLoop` (default true), `initialTimestamp`, `sendSetTimestamp`, `onComplete`, `onNext` and `onPrevious` (`ScenePlayer.tsx:221-231`). It needs no context a plugin has to supply.
- It records the watching itself, as on the scene page (`track-activity.ts`): `sceneSaveActivity` with the resume time and the seconds played every 10 s and on each pause, end, scene change and unmount, and `sceneIncrementPlayCount` once per scene load when the seconds played reach `ui.minimumPlayPercent` of the length. That setting defaults to 0, so any play of a second or more counts a play, and the count lands when the next scene loads at the latest. At 98% or more the resume time goes back to 0. `ui.trackActivity` (default on) turns all of it off.
- A scene starts at its `resume_time` unless `ui.alwaysStartFromBeginning` is on or `initialTimestamp` is set (`ScenePlayer.tsx:687-699`), and plays by itself when `autoplay`, its control bar's auto-start toggle or `interface.autostartVideo` says so (`:705-712`). Watch This passes no `autoplay`, so Stash's Auto-start video setting decides.
- `onComplete` is attached to the player's `ended` event, and the effect's cleanup calls `player.off("ended")`, which removes every `ended` listener, track-activity's too (`:909-916`). The effect runs again whenever `onComplete` changes, so Watch This passes one module-level function for it and for `sendSetTimestamp`.
- A new `scene` prop keeps the player and swaps its source, as the scene page's queue does: the old scene's activity is saved and its play counted, if it reached the minimum, by `trackActivity().reset()` before the new source loads (`ScenePlayer.tsx:578-589`). So the play Stash records for a look before Watch This's Skip lands at the moment of the skip, and the snooze ladder lets a play within two minutes of a skip pass (`LOOK_MS`, `model/watch.js`). Whether the pick was watched is Watch This's own measure instead: the time the player spent playing it (between `playing` and `pause`, `waiting`, `ended` or `emptied`), as track-activity counts play time; a tenth of the scene's length or more resets the ladder (`WATCHED_SHARE`). After a source swap, video.js can keep `vjs-playing` on the player while the video element is paused, since the media load algorithm fires no `pause`.
- `onNext` and `onPrevious` go to the `skipButtons` plugin (`:448-454`, `PlaylistButtons.ts:19-29`): a defined handler adds `vjs-skip-buttons-next` or `-prev` to the player, which shows the control bar's next or previous button (`styles.scss:256-266`), and `MediaTrackNext` and `MediaTrackPrevious` call it (`ScenePlayer.tsx:126-138`), as do the media session's next-track and previous-track actions (`media-session.ts:53-58`); an undefined handler hides the button and the keys do nothing.
- The player calls `focus()` when it starts and when a scene loads (`:429`, `:703`). With focus, Space and Enter play and pause, ↑ and ↓ change the volume, ← and → seek, and the digits jump to tenths of the scene (`:59-201`). A click outside the player gives the arrow keys back to the page.
- `.VideoPlayer` is a flex column, `max-height: calc(100vh - 4rem)` and `height: 100vh` from 1200px; `.video-wrapper` is `56.25vw` high below 1200px, its parent's height above, and `177.78vw` for a portrait file (`styles.scss:11-35`). That CSS comes with the lazy player module, after the plugin's stylesheet, so a plugin rule needs more classes to win a tie. The scrubber (`.scrubber-wrapper`, 122px plus 5px margins) shows when the window is at least 450px high and not a phone, unless `hideScrubberOverride` (`:303-318`); the scene page starts that from `interface.showScrubber` (`Scene.tsx:792-794`), and Watch This does the same.
- On the scene page the player sits in `.scene-player-container` (`Scene.tsx:1033`), which `runtime/watching.js` listens to; Watch This's player sits in `.cherrypick-watch-player`, which it listens to as well.

## Plugin configuration (tier 1)

- `configurePlugin(plugin_id, input)` replaces the plugin's whole map and writes `config.yml` (`internal/api/resolver_mutation_configure.go:717-729`). No hook fires.
- Nested maps survive, but numbers inside arrays come back as strings after a restart: Stash's YAML writer has no case for `json.Number` inside arrays. Cherry Pick stores each data key as one JSON string.
- Settings › Plugins snapshots every plugin's configuration once when the Settings page mounts (`components/Settings/context.tsx:149-167`). Toggling any plugin's setting writes every plugin's map from that snapshot (`:506-531`), so a write Cherry Pick made while the page was open is lost. Cherry Pick defers its writes while the Settings page is open and keeps a browser mirror that restores a missing or stale map.
- Stash's own `useConfigurePlugin` evicts the cached `Configuration` query after a write; Cherry Pick does the same with `utils.StashService.evictQueries`, so the next snapshot is current. Each eviction refetches Stash's configuration, so writes are debounced.
- Settings › Plugins renders a BOOLEAN with no stored value as off, and its first click stores `true`. Cherry Pick writes its defaults once at first load so the switches match what it does.
- `PluginApi.hooks.useSettings()` returns the Settings page's state: `plugins`, its copy of every plugin's map, and `savePluginSettings(pluginID, map)`, which each plugin switch calls with its copy and the new value (`components/Settings/SettingsPluginsPanel.tsx:83-101`). A row added after `PluginSettings` renders inside that page's context, so it can change a setting the way a switch does: the switch above it moves, Stash writes every plugin's map half a second later, and the next toggle on the page carries the change. Outside the Settings page `useSettings` throws (`components/Settings/context.tsx:87-92`). The same in develop.
- The manifest is parsed strictly: an unknown key makes Stash skip the plugin. `ui.csp` accepts only `script-src`, `style-src` and `connect-src`.

## Custom fields (tier 2)

- `CustomFieldsInput { full, partial, remove }` (`graphql/schema/types/metadata.graphql:369-376`). `partial` upserts per key; `remove` deletes keys after the set; if both `full` and `partial` are sent, `full` wins and `partial` is ignored (`pkg/sqlite/custom_fields.go:33-61`).
- Values must be scalars; arrays and objects are rejected.
- `performerUpdate` fires `Performer.Update.Post` for other installed plugins with hooks (`internal/api/resolver_mutation_performer.go:433`), so Cherry Pick writes once per finished bracket.
- The performer page shows every custom field, and `PerformerFilterType.custom_fields` filters on them (`EQUALS`, `GREATER_THAN`, `NOT_NULL` and others).
- The performer edit form re-submits `custom_fields: { full }`, so a stale edit form can overwrite a concurrent plugin write.
- Scenes take custom fields the same way: `sceneUpdate` accepts `custom_fields`, and `SceneFilterType.custom_fields` filters on them (checked on v0.31.1). Cherry Pick writes one there, `cherrypick_provisional`, in the same `sceneUpdate` or `performerUpdate` that sets a rating Apply stepped down from a champion's, so a provisional rating costs no extra write.

## The library and scene brackets

- `SceneFilterType.updated_at` compares the value sent with the time Stash stores as text in the server's own zone. On a server at UTC−4 (v0.31.1 started with `TZ=America/Toronto`), a UTC value ten minutes back matched 0 of 8 scenes and the same moment in local time matched all 8. Stash returns `updated_at` as the right instant with the server's offset (`2026-10-17T00:15:31-04:00`) and `last_played_at` and `o_history` in UTC. So `data/library.js` sends no timestamp filter: it sorts by `updated_at`, `last_played_at` or `last_o_at` (descending, ties by id) and compares the times in the browser.
- `sceneAddPlay`, `sceneAddO` and `sceneSaveActivity` leave `updated_at` alone; `sceneUpdate` moves it.
- `findScenes` takes `ids: [ID!]` (with `filter: { per_page: -1 }`).
- An audio-only file comes back with `video_codec: ""` and a width and height of 0.
- `paths.vtt` is `/scene/<hash>_thumbs.vtt` (also served at `/scene/{id}/vtt/thumbs`): `WEBVTT` with 81 cues over the runtime, each `<hash>_sprite.jpg#xywh=x,y,w,h` (160×90 for 16:9), the sprite path relative to the list. It answers 404 when Stash hasn't generated sprites, and `paths.vtt` is set either way. The sprite sheet is JPEG and the preview (`paths.preview`, `/scene/{id}/preview`) H.264, whatever the scene's codec.
- `/scene/{id}/preview` answers HEAD with 405, a GET with `Range: bytes=0-0` with 206, and 404 when Stash hasn't generated the preview. Serving it records nothing. Stash's own `ScenePlayer` saves activity as it plays and counts a play, and its ←/→ keys seek, so scene brackets never use it.
- `configuration.interface.soundOnPreview` says whether Stash's previews play with sound; `configuration.general.previewSegments × previewSegmentDuration` is a preview's length (12 × 0.75 s = 9 s by default).

## StashDB

- `https://stashdb.org/graphql` answers cross-origin requests (`Access-Control-Allow-Origin: *`, `apikey` allowed) and authenticates with the `ApiKey` header. Stash's default CSP blocks it; the manifest's `ui.csp.connect-src` adds it.
- Stash's own stash-box queries cannot list a performer's scenes or return submission counts, so Cherry Pick queries StashDB from the browser with the user's key, read from `configuration.general.stashBoxes`.
- A performer's scenes: `queryScenes(input: { performers: { value: [id], modifier: INCLUDES }, sort: POPULARITY, per_page: 100 })`. `POPULARITY` orders by distinct users who submitted fingerprints; the count itself is not exposed. `TRENDING` drops scenes with no submissions in the last 7 days.
- "Held by about N": the sum of `submissions` over a scene's OSHASH fingerprints, an approximation.
- StashDB has no similar-scenes query; More like this queries by the scene's performers and studio and ranks in the browser.
- Requests from the browser go one at a time, at least a second apart, at most six per page view, and are kept in IndexedDB for 30 days (`src/js/stashdb/client.js`). An answer over 7 days old, or kept in an older cache format, is used and asked for again once the page's own lookups are done, inside the same per-view budget; the new answer is only stored, so a page never changes while it shows. A scene page has at most five lookups, so its refreshes fit beside its misses. A page asks only for its own lookups: a performer's Scenes tab one request, a scene page up to five, New in your library up to three.
- The Connect StashDB dialog validates a key with Stash's `validateStashBoxCredentials` and adds it with `configureGeneral(input: { stashBoxes })`, sending back every other stash-box as `configuration.general.stashBoxes` reports it. Stash 0.31 and develop write a stash-box's `max_requests_per_minute` to `config.yml` as `maxrequestsperminute` and read it back as `max_requests_per_minute`, so the API always reports 0 and any save, Stash's own included, resets the limit to the default.
- The compatibility tests reach the mock stash-box without a localhost CSP entry or a switch in the plugin: Playwright answers the browser's requests to `https://stashdb.org/graphql` from the mock, rewrites the endpoint of `validateStashBoxCredentials` on its way to Stash, and the test browser cannot resolve `stashdb.org` (`tests/stashdb.spec.mjs`).

## Beside Ascension and HotOrNot

Checked against Ascension 1.4.1 (`Release/ascension.js` and `asc_taskmaster.py` in Sakoto's repository), against the source of HotOrNot 1.0.0 (`hotornot`), HotOrNotV2 2.1.0 (`hotOrNotV2`) and HotOrNot_V3 3.1.0 (`hot_or_not`), and live beside Cherry Pick for Ascension 1.4.1 and HotOrNot 1.0.0 on Stash v0.31.1. Ascension's own pages were opened with Cherry Pick enabled on 2026-10-16: the battle dialog in Head to Head, Placement, Champion and Scene modes, Performer Statistics (Leaderboard and Tier Distribution), Options, the Metrics Dashboard on `/stats`, and all nine tasks, at 1440px and at 390px under Juicy and Leather. Nothing threw and no piece of either plugin covered the other's.

- Stash takes a plugin's id from its manifest's file name (`pkg/plugin/config.go:443`). Ascension 1.4.1's zip installs two plugins named Ascension: `ascension` (the release) and `ascension-beta` (1.4B, whose description says to disable the release before running it). Stash enables both on install. HotOrNot's builds are `hotornot`, `hotOrNot`, `hotOrNotV2` and `hot_or_not`. Cherry Pick finds them in Stash's `plugins` query by id or name, enabled only (`model/rankings.js`).
- Every match calls `performerUpdate` or `sceneUpdate` with the new `rating100` and `custom_fields: { partial }`: `hotornot_stats` (a JSON string) and `performer_record` or `scene_record` (a JSON list of the last 30 matches). Older HotOrNot data has `elo_matches`. Any of the four marks a ranked record: Apply never writes its rating, checks again right before writing and before an Undo, and the model reads it as unrated.
- The Prime tasks write `rating100` alone. "Prime Unrated Performers" and "Prime Unrated Scenes" give 70% of the unrated records one shared random value in 1-9, 25% one in 25-39 and 5% exactly 40 (`[random.randint(1, 9)] * num_f` repeats one draw). They count a rating of 1 or less as unrated, so they also overwrite a record Ascension's own matches left at 1. Cherry Pick recognises Prime's values only when they cover more than half of a group's ratings: run on a library that is mostly rated already, they read as the user's. "Prime Scenes From Performer Ratings" writes computed scene ratings, only for scenes whose performers have Ascension matches; nothing tells them apart from the user's, so they still reach the model (live: 22 of the demo library's 26 unrated scenes, and the model's 48 rated scenes became 70).
- Your score shows on a scene whose only rating another plugin set (`unratedByYou` in `model/index.js`): ranked, mirrored or primed. Up to 0.1.0 it showed only where `rating100` was empty, so after "Prime Unrated Scenes" on a library that was mostly unrated, none of the primed cards carried it. On such a card Stash's banner holds the other plugin's number, and `css/10-score.css` hides it (`.scene-card-link:has(> .cherrypick-score-banner)`); Ascension and Xenith hide it themselves while they are enabled. The check compares the card's `rating100` with the one the model read, so a rating the user sets on the card hides Your score straight away.
- The tasks run Ascension's Python backend, which imports `requests`. Stash runs `python3` for a manifest that says `python` when there is one on its PATH (live on macOS, where `/usr/bin/python3` has no `requests`, every task failed until Stash's PATH led to a Python that has it).
- Ascension's own badge calls any rating without match history "Primed", including ones set by hand or by Apply, and it starts ranking from whatever rating a record has.
- On each scene and performer card, Ascension hides the first `.rating-banner` with inline styles (`visibility: hidden; height: 0` and more), taking it for Stash's rating, and adds `.hon-asc-score-display` at the bottom left of the thumbnail. On an unrated scene the first `.rating-banner` is Your score, so the badge drops inline styles it did not set (`features/scoreBadge.jsx`).
- HotOrNot 1.0.0 is the plugin Ascension was forked from. Every match calls `performerUpdate` with the new `rating100` and `custom_fields: { partial: { hotornot_stats } }` (a JSON object: `total_matches`, `last_match`, `wins`, `losses`, `current_streak`, `best_streak`, `worst_streak`), and `imageUpdate` with a rating alone. V2 writes the same field; V3 adds `performer_record`. Apply's check reads `hotornot_stats`, so all three builds' ranked performers count as ranked. Its dialog opens only for performers and images, so no scene gets a record.
- HotOrNot 1.0.0 puts nothing on scene or performer cards. It adds a 56px button, `#hon-floating-btn`, fixed at the bottom right of the Performers and Images pages (20px from the edges, 60px from the bottom at phone width) with `z-index: 9999`, and appends a rank badge, `#hon-battle-rank-badge` ("Battle Rank #11 of 47"), to the parent of the performer page's first `.rating-stars`. Neither overlaps a Cherry Pick piece on the page. Ascension uses the same badge id, so the two fight over a performer's page when installed together, with or without Cherry Pick.
- Ascension's battle dialog (`#hon-modal`, `z-index: 1000`) sits under Stash's own navbar, which moves to the bottom of the screen at phone width (`z-index: 1030`), so the navbar covers the dialog's bottom 49px (63px under Juicy and Leather). The same happens with Cherry Pick and the themes disabled. The cards scroll inside the dialog, and the arrow keys pick.
- The Metrics Dashboard on `/stats` asks for `/plugin/ascension/assets/` and logs a 404 until Ascension's Snapshot task has written a file there.
- The button's `z-index` is above Stash's modals (`.modal-backdrop` 1040, `.modal` 1050). At phone width Cherry Pick's dialogs are full screen and gather their buttons at the bottom right, so on the Performers page the button covered "Undo the final pick" in the champion dialog. While one of Cherry Pick's dialogs is open, `css/40-brackets.css` sets the button's `z-index` to 1000: `body:has(.cherrypick-dialog) #hon-floating-btn`. The compatibility test samples nine points across every control in the play, champion and Apply dialogs at 390px and fails if any hits the other plugin's pieces.
- HotOrNot's dialog (`#hon-modal`, `z-index: 10000`) draws a random gender from every chip but Male and shows "Not enough performers" until a draw has two performers, so the test turns the other chips off before it plays a match.
- HotOrNotV2's source inserts `.hon-star-rating` at the start of each performer card's `.card-section` (or `.card-body`), in the card's flow rather than over the thumbnail; a switch in its settings turns it off, and its button goes in the top navbar. Neither V2 nor V3 has run beside Cherry Pick.
- Match histories, checked against Ascension 1.4.1 (`Release/ascension.js:3228-3246` for scenes, `:3372-3386` for performers), HotOrNot_V3 3.1.0 (`hot_or_not.js:1103-1199`) and Xenith 3.2.0 (`src/hooks/usePair.js:404-420` and `:503-519`, `src/matchmaking.js:27-34` and `:160-176`). Each is one JSON string per record: Ascension's and V3's `performer_record` (the last 30, `{ date, opponent: "<id>:<name>", won }`, with `AscRatingAfter` from Ascension and `ratingAfter` from V3), Ascension's `scene_record` (the last 30, `{ date, opponentId, won, ratingAfter, AscRatingAfter }`) and Xenith's `xenith_record` on performers and scenes (the last 50, `{ date, opponent: "<id>:<name or title>", won, ratingAfter }`). Ascension 1.4.1's Skip writes nothing, and its draw (`won: null`) has no button; a skip writes `won: null` in V3 and `{ draw: true }` with no `won` in Xenith; an unknown opponent is `0`. Ascension writes both players' records in parallel, V3 writes the loser's after the winner's update returns, and Xenith gives both one date. With Learn from Ascension, HotOrNot and Xenith matches on, `model/matches.js` reads all three fields on every performer and scene as picks, one per match. Live on Stash v0.31.1, 79 matches played in Ascension's dialog and 20 in Xenith's (with 4 Xenith draws and an Ascension skip and undo) came out as 99 picks, one per match, and the Ascension entries Xenith copied counted once.

Checked against the source of Binge 0.14.2 (`ordureconnoisseur/binge` at `098c5d2`) and Advanced Rating 3.1.1 (`ordureconnoisseur/stash-advanced-rating` at `11f51a7`) on 2026-10-18. Neither has run beside Cherry Pick, and the Compatibility workflow has no leg for them.

- A star tap in Binge writes `rating100` directly when Advanced Rating is not installed. When it is, the tap opens Advanced Rating's scores, which Binge writes as score tags with `tag_ids`. Collections are `tag_ids` too. Its review editor (`src/scribe/api.ts`) writes custom fields only through `partial` (`stashScribe_review`, on scenes and performers) and takes an older review block out of `details`. - Advanced Rating's score tags are named `<Criterion> ★: <0-5>` (`Production Quality ★: 4`), each under its criterion's `<Criterion> ★` and that under `Advanced Rating System` (`Advanced Performer Rating` for performers). A record with score tags is rated, so Apply leaves it alone. - Both plugins query StashDB from the browser with the user's key. Binge looks up scenes' performers 5 requests at a time, each batching scenes by alias (`src/api/stashdb.ts`). Cherry Pick's client sends one request a second and rests for ten minutes after a 429 (`src/js/stashdb/client.js`).

## Beside Stash TV

Checked against the source of Stash TV 2.34.1 (`secondfolder/stash-tv` at `1ba2a2c`) on 2026-10-19. It has not run beside Cherry Pick, and the Compatibility workflow has no leg for it.

- Stash TV's feed is its own app at `/plugin/stash-tv/assets/app/`, so Cherry Pick's patches never run there and Cherry Pick sees no swipe, only what Stash records.
- Each scene slide plays in Stash's own `ScenePlayer`, built from Stash's source, with `trackActivity` on (`packages/tv-ui/src/components/slide/MediaSlide/index.tsx`: `trackActivity={!scenePreviewOnly && props.mediaItem.entityType !== "marker"}`). Stash records plays, play time and resume points as on the scene page (see Watch This's player), at the same `ui.minimumPlayPercent`. Its preview-only mode and marker slides record nothing.
- At the default minimum of 0, a swipe past a scene after a second of play records a play with that second of play time, so a feed session leaves many plays with little time behind them. `playWeight` (`model/behaviour.js`) counts a scene's plays only as far as its play time pays for them, one play per tenth of its length (`WATCHED_SHARE`, Watch This's line between a look and a watch). A scene played for less than a tenth in all has no behaviour score, adds nothing to For you's momentum or rewatch rate, and For you's freshness reads it as never watched (`looked`, "Not watched yet"). Plays with no play time at all, added by hand or recorded before Stash kept play time, count in full.
- Its rating and O buttons write through `sceneUpdate` (`hooks/useSceneUpdate.ts`) and `sceneIncrementO` and `sceneDecrementO` (`hooks/useOCounter.ts`), with nothing that marks them, so they count as the user's own.
